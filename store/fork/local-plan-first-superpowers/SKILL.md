# 先想清楚再动手

**一句话**：判断这活要多少铺垫 → 想清楚意图 → 出方案等点头 → 才动手。

## 第一步：分类（说出来，让人能纠正）

动手前先判断这活属于哪类，**并把判断说出口**（"这看着是改良类，我在这儿给个短方案，不写文档"）——
说出口就给了人纠错的机会。

| 路径 | 什么时候用 | 产出 |
|---|---|---|
| **探路** | 只是想验证"能不能/行不行"，答案本身就是产出 | 2–3 句说明要探什么 → 点个头 → 用最省的方式探 → **给结论**（探出来的东西一律标成"可丢弃"） |
| **改良** | 对**已有**东西的有界改动（改一处、加一项、修一个 bug） | 逐个澄清 → **短方案**（几句话到一小段）→ **停下等明确 yes** → 才动手（不写计划文档） |
| **新建** | 从零开始，或改动会波及结构/别人依赖的东西 | 澄清 → 2–3 个方案带权衡 → 分节呈现设计 → 写设计文档 → 自审 → 用户审 → 才动手 |

**怀疑时选更重的那条。棘轮只升不降**：中途发现隐藏复杂度 → **停下、说出来、升级路径**，
绝不闷头做完再讲。

## 第二步：想清楚 —— 动手前必须答得出这四个问题

1. **目标**：做成什么样算成功？给谁用？
2. **边界**：动哪些、**不动哪些**（后者同样重要）
3. **已知的坑**：以前踩过什么、有哪些约束
4. **怎么验证**：做完怎么知道对了

**答不上第 1 条就别动手** —— 那是没想清楚，不是"这活简单"。

**把理解写回去**：用短句复述你听到的目标、约束、成功标准，**并区分"你说的"和"我猜的"**，
请人纠正。需求里已经说清目的和约束时，**直接复述**就好，别把同样的问题再问一遍。

## 第三步：出方案，不是出结论

- 给 **1–3 个选项**，各带代价，别只给一个"最优解"
- **推荐放前面**，说清推荐哪个、为什么
- 涉及取舍就**摊开讲**，别替人拍板
- **YAGNI**：每个方案都砍掉不必要的部分

## 第四步：硬门控

**点头之前不碰实际改动。** 读、探索、分析可以做；写操作不做。

**批准的是你实际呈现的那个阶段**：点头"想法"不等于批准"还不存在的产物"，
也不等于豁免后面的步骤 —— 一个个来。

## 动手前的三个问题（踩过的教训）

1. **用户是不是已经给过位置 / 答案了？** —— 先看他说的，别自己从头推导
2. **现场有什么直接证据？** —— 进程在跑？文件在？索引在？（**别信二手信息**，比如从快捷方式里解析出的路径）
3. **我自己定的规则怎么说的？** —— 尤其是"一份实体 + 多 agent junction"这类结构约定

**三次同源的错误**（都是"依赖推导"而不是"看事实"）：

| 错误 | 我依据的 | 事实就在哪 |
|---|---|---|
| 搜不到某个目录 | 我设的 `maxdepth` 不够 | 用户已经给了准确路径 |
| 断言某软件"没装" | 从 .lnk 解析出的旧路径 | 用户说的地方有，进程还跑着 |
| 复制完留下两份 | 想当然"复制过来就行" | 我自己写的规则要求建 junction |

**共性**：我在**从线索推导**，而事实往往**就在眼前**（用户知道、现场能查、规则是我写的）。
推导只在没有直接来源时才用 —— 有来源就先看来源。

## 什么时候直接跳过

- 用户明说"别问了直接做"
- 纯查询、纯解释、纯闲聊
- 已经在执行中的连续步骤（别每步都停下来问）

## 红旗：这几个念头一冒出来，就该停

| 念头 | 实际 |
|---|---|
| "太简单了，不用想" | 按分类走：改良类只要两三句短方案。**门是"批准"，不是"设计的长度"** |
| "我把它归成改良，就能跳过文档" | 为了省事去贴标签 —— 这本身就是疑点，**选更重的那条** |
| "方案显而易见，我边写边等他看" | 门是批准。呈现完就停，等到明确的 yes |
| "我熟这类活，所以是改良" | 改良衡量的是**手上这个东西**，不是你的熟悉度。没有现成东西可改 = 新建 |
| "探路成功了，所以东西留着" | 探路的产出是**答案**。留下东西 = 新需求，**重新分类** |
| "它变大了但我快做完了，不用重分类" | 隐藏复杂度**只升不降**。停下，说出来 |
| "他批准了探路，后续改动就一起批了" | 每件事**各有各的分类、各有各的批准** |

## 别做过头

- **不上子代理** —— 耗 token，多数任务不值
- **不写规格文档** —— 除非分类到"新建"或用户明确要
- **不为了流程而流程** —— 分类的意义就是让"顺手的活"别被流程拖累
- 方案本身也要**简短**：三句话能讲完就别写成十条
