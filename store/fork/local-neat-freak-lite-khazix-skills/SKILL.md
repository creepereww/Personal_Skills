# 洁癖·精简版 — 知识收尾审查

> 不写代码的项目，收尾时把记忆和文档对齐、压扁、清干净。

## 定位：它是原版的哪一部分

原版 `neat-freak` 面向软件项目，一半检查项在**没有代码的项目里全部空转**——只白烧上下文。这一版只留下跟代码无关的通用部分：

| 保留 | 砍掉 |
|---|---|
| 记忆毕业机制 | 代码事实提取（15 项） |
| 反膨胀红线 | API / 路由 / 环境变量 / 配置文件一致性 |
| 相对时间清理 | CI/CD、依赖版本、项目元数据 |
| 文档内链接有效性 | CHANGELOG 与代码比对、Monorepo、测试结构 |
| 合并重复、删除废弃 | 代码逻辑 vs 架构文档一致性 |

## 事实基准：非代码项目怎么办

原版的原则是"代码是事实基准，文档向代码对齐"。**没有代码时，事实基准改成交付物本身**：

- 知识库类 → 那个 HTML 文件的实际章节、编号、结构
- 文件整理类 → 整理后的实际目录树与命名规则
- 纯文档类 → 文档声称的 vs 它实际写的

**没说清事实基准就先问一句，不要猜。** 猜错会让整轮审查空转。

## 三类文档，三种受众

| 位置 | 受众 | 装什么 |
|---|---|---|
| Agent 记忆（`.workbuddy/memory/`、全局 `MEMORY.md`） | Agent 自己跨会话用 | 个人偏好、非显而易见的事实、近期教训 |
| 项目内规则文档（`CLAUDE.md` / `AGENTS.md`，或你的 `整理规则.md`） | 当前项目里的 AI | 规则、红线、命名与分类约定、踩坑警示 |
| 项目内说明文档（`README.md` / `docs/`） | **其他人**和未来的 Agent | 怎么用、怎么接手、结构说明 |

- **规则文档 ≠ 变更日志**：不写"X 日起改成 Y 规则""详见 xxx.md"这类历史叙事，那是 git log 和 CHANGELOG 的活
- **两类文档受众不同、不能互相替代**：规则文档写"AI 该怎么做事"，README 写"这东西能做什么"
- **`CLAUDE.md` 和 `AGENTS.md` 功能等价，只维护一个**——另一份用一行 `See CLAUDE.md` 跳转。两份同时维护必然不一致

**规则文档该有哪 6 块**（非代码项目版，从 11 板块基线里挑出来的）：

1. 这份规则管什么（1-3 行）
2. 目录结构 —— 每个目录放什么、不放什么
3. 硬边界与红线 —— 什么绝对不能做
4. AI 行为守则 —— 操作前必须做什么
5. 命名 / 分类 / 编号规则
6. 常见陷阱 & 已知问题

完整清单（规则文档 11 板块、说明文档 11 板块、docs/ 命名规范、质量红线、从零建立的建文件顺序）见 **[references/doc-standards.md](references/doc-standards.md)**——只在建文档或审查文档质量时才读。

## 什么该进规则文档（净涨幅红线的判据）

判断一句话：**下次干活时如果没看到这条，会不会犯错？**

| ✅ 该进 | ❌ 不该进 |
|---|---|
| 硬边界与红线（哪类目录不许动、什么必须先备份） | 历史叙事（"X 日起改成 Y 规则"） |
| 命名 / 分类 / 编号规则 | 详细机制说明（归说明文档或知识库本身） |
| 操作与命令速查 | 单次事故复盘（归记忆，或直接删） |
| 踩坑警示（会再踩的那种） | "详见 xxx.md" 的指针句（用文档内的链接表代替） |
| 文档 / 知识库的结构索引 | bug 修复流水账 |

**这张表就是「净涨幅 ≤30 行」那条红线的判据**——加之前先对照，往 ❌ 那列加就是在制造膨胀。

## 机制一：记忆毕业（防膨胀的根）

文档靠就地编辑收敛（改 10 次还是那一份），记忆天生只追加（每条教训生一个新文件，旧的不删）。没有反向阀门，memory 会堆到比文档还大，稳定知识被困在几十个松散文件里——既进不了上下文，也没沉淀成能给人看的东西。

**满足任一条就「毕业」**：内容并进项目内 markdown，原记忆文件删掉或缩成一行指针。

- **同一主题的教训反复出现到第 3 次** → 已是稳定知识，不是"最近踩的坑"
- **它讲的是"系统/文档怎么工作"**，而不是"我们踩过什么坑、做过什么决策"
- **它是"X 已上线 / 已落地 / 已就位"的事件记录** → 结论进文档，过程进 git log 或 CHANGELOG，记忆不留常驻

**判据一句话**：「下一个接手的人（不只是我自己）需要知道这件事吗？」需要 → 它属于文档，不属于记忆。

按前缀看生命周期：`reference_` 通常可长期常驻；`feedback_` 稳定后毕业；`project_` 多数是事件记录，**是优先毕业 / 删除的对象**。

> **毕业是跨 Agent 唯一可靠的传承方式。** Agent 私有记忆目录（`~/.workbuddy/MEMORY.md`、`.workbuddy/memory/`、`~/.claude/projects/…/memory/`）换 Agent 读不到；只有**项目目录里的 markdown** 是任何 Agent 打开就能读的。所以"换 Agent / 开新对话能延续进度"的前提，是稳定知识已经泵进项目内文档。

## 机制二：反膨胀红线（硬）

| 对象 | 上限 | 超了怎么办 |
|---|---|---|
| 记忆索引 `MEMORY.md` | **≤200 行 且 ≤25KB（硬）** | 超出部分在会话开始时**静默不加载 = 等于没记**。压法不是硬删，是毕业 |
| 单条记忆文件 | ~100 行（软） | 拆 / 删 / 提升进文档后缩成指针 |
| 项目内规则文档 | 净涨幅 ≤30 行 / 次 | 超了说明在写历史叙事，不是补规则 |
| 记忆目录 vs 文档目录 | 记忆不应更大 | 倒挂 = 本该毕业的知识还赖在记忆里 |

**超尺寸是最高优先级，大于"补本次会话漏掉的内容"。** 超 25KB 的部分根本不进上下文，补再多也是白补。

## 机制三：相对时间清理

记忆和文档里**永远用绝对日期 `YYYY-MM-DD`**，不写"今天 / 昨天 / 最近 / 上周 / 刚刚 / 下次"。相对时间过一周就变成错误信息。

收尾时用 Grep 搜一遍清零：

```
今天|昨天|最近|上周|刚刚|下次|稍后|前段时间|today|yesterday|recently|later|soon
```

## 执行流程

### 第零步：尺寸体检（先查，不达标先精简）

用 Read 工具看行数和体积，**不要依赖 `wc -l` / `du`（Windows 不可用）**：

- 记忆索引是否 ≤200 行且 ≤25KB
- 有没有单条记忆超 ~100 行
- 记忆目录总体积是否大于文档目录

**先精简，再补漏，两件事不能混着做**——精简时心态是"什么不该在这"，补漏时心态是"什么该补到这"，混着做两头不到位。

### 第一步：盘点现状（强制枚举，不能跳）

- 列记忆文件：`.workbuddy/memory/*.md`（含每日日志）、全局 `~/.workbuddy/MEMORY.md`
- 列项目内 markdown：`CLAUDE.md` / `AGENTS.md` / `README.md` / `docs/` / 各类规则文档
- 各平台的记忆与技能路径速查见 `references/agent-paths.md`
- 确认事实基准（知识库 HTML / 目录树 / 文档本身）
- 回顾本次对话全部内容

输出一张内部文件清单，每个标「评估过 / 要改 / 不用改」。**漏一个不行**——这是最容易翻车的地方。

### 第二步：识别变更

看新事实会波及哪些层级，而不是只看本次对话多了什么：

- **新定下的规则** → 项目内规则文档 **和** 记忆里对应条目都要动（两边都写，不能只写一处）
- **已完成的待办** → 删掉，留着会变成噪音
- **重复主题** → 合并，不新增
- **过期事实** → 改，不追加
- **稳定下来的教训** → 走毕业流程
- **跨目录 / 跨项目改动** → 两边各跑一次完整盘点，不要假设改了一边另一边就不用管（这是最常见的漏改）

遇到不确定的改动，查 **[references/sync-matrix.md](references/sync-matrix.md)**（非代码版的变更影响清单，按需读）。

### 第三步：实际修改

**真的用 Edit / Write 改，别只描述"我会怎么改"。**

编辑原则（按优先级）：

- **减优于加**（最重要）：项目内规则文档净涨幅 >30 行是红灯——回头审，加的是规则还是便条
- **合并优于追加**：新加条目前先 grep 同关键字，看现有条目能不能并
- **删除优于保留**：完成的计划、推翻的决策、单次事故流水账 → 删
- **毕业优于内部挪腾**：稳定知识往项目内文档泵，别在记忆里搬来搬去
- **精确优于冗长**：一条记忆说清一件事，别塞三件
- **受众不混**：项目内规则文档不抄记忆原文，记忆里不写"我记得上次……"

### 第四步：自检（四大项，逐条过）

**先确认一件事**：第一步列的那张文件清单，**每一个**都标了「不用改」或「已改」——漏一个就回头补。这是防漏改的总闸。

**一、反膨胀**
- [ ] 记忆索引 ≤25KB 且 ≤200 行
- [ ] 没有单条记忆超 ~100 行
- [ ] 记忆目录总体积不大于文档目录
- [ ] 项目内规则文档本次净涨幅 ≤30 行，且加的东西都落在「✅ 该进」那一列
- [ ] 没塞进"X 起 Y 上线"这类历史叙事条目

**二、毕业**
- [ ] 反复出现到第 3 次的主题已毕业进文档
- [ ] 事件记录类记忆已处理（结论进文档，记忆不留常驻）
- [ ] 每条记忆的 description 和内容对得上
- [ ] 记忆之间没有互相矛盾

**三、相对时间**
- [ ] Grep 搜相对时间词清零

**四、事实与链接有效性**
- [ ] 规则文档与说明文档里提到的**每个目录 / 文件 / 命令**，实际都存在、可执行（文档写"截图放 Screenshots/"但该目录不存在 = 文档错；写"运行 sort.py"但文件已删 = 文档错）
- [ ] 说明文档里的操作步骤，照着走一遍能走通
- [ ] 抽走所有 markdown 里的相对链接 `[…](…)`，逐一验证目标存在
- [ ] 文件重命名 / 移动后，旧链接已更新
- [ ] 记忆索引里每个链接都指向存在的文件

**自检边界（防幻觉越权）**：自检清单是**封闭的**，只逐项核对上面这些，**不要自创检查项**。清单外发现的真实问题 → 标注 ⚠️ 列入「未处理」，**不要顺手就改**。自创问题 → 改文档 → 摘要里写"自检发现并修复"，这是越权，不是洁癖。

### 第五步：变更摘要

```
## 同步完成

### 记忆变更
- 更新：xxx（原因）
- 新增：xxx
- 删除：xxx（原因）
- 毕业进文档：xxx → <文件>.md

### 文档变更
- <文件> — xxx

### 未处理
- xxx（为什么没处理）
```

只列有实际变更的条目，没改的不写。

## 从零建立规则文档：先出清单，等你确认

**触发条件**：项目里还没有规则文档（`CLAUDE.md` / `AGENTS.md` / `整理规则.md`）或说明文档时走这个模式。**不要直接动手写。**

1. **提取事实** —— 按"事实基准"盘点现状：有哪些目录、文件怎么命名、现存哪些说明文件、本次对话定了哪些规则
2. **出审查报告** —— 列出缺失项、不一致项、该迁移的散落文件、记忆层的毕业候选。格式见 **[references/init-report-template.md](references/init-report-template.md)**（只在从零建立时才读）
3. **出操作清单等确认** —— 按优先级分组，末尾明确写"请确认以上操作"：

```
### 🔴 先修不一致
- [ ] <文件> — <改什么>

### 🟡 新建文件
- [ ] <文件> — <装什么>

### 修改 / 迁移
- [ ] <文件> — <改什么>
```

4. **收到确认才动手** —— 部分确认只做确认的部分；要求调整就改方案重新确认；取消就一个字不动
5. **写标记** —— 执行完在规则文档末尾加 `<!-- neat-freak-lite: established at YYYY-MM-DD -->`（用执行当天日期，别照抄示例）。审查后无需任何变更的，仍写标记并记录"已审查，无需变更"

**与常规同步的核心区别就在这里**：常规同步自己拍板，从零建立必须等你点头。

## 特殊情况

**记忆之间出现无法自动判断的矛盾** → 列入「未处理」让用户决定。这是常规同步中唯一需要用户介入的情况，其他都自己拍板（从零建立模式另有确认要求，见上一节）。

**本次对话没有产生新事实** → 照样审查过期 / 冲突 / 相对时间，审查本身就有价值。

**发现交付物本身有问题**（知识库章节错乱、目录结构不合理、规则文档自相矛盾）→ 标注 ⚠️ 列入「未处理」，建议用户修交付物。**不要为了"对齐"把文档改成错的样子。** 文档描述"应该怎样"，交付物实现"实际怎样"——交付物是错的，改交付物不是改文档。

**发现之前的同步漏了东西** → 修掉。你就是这个项目的持续编辑，过去的漏洞也归你管。

## 安全边界

- **只改记忆和文档，不碰交付物本身**——HTML 知识库内容、被整理的文件，一律不动
- **涉及删除记忆文件**：先列清单，不静默删
- **个人文件操作**（Desktop / Downloads / Documents）不在本技能范围内，走文件整理流程：只读扫描 → 用户确认 → 走回收站 → 先备份
