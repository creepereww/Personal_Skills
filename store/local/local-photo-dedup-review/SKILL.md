# 照片查重整理

**改我时要守什么**：本 skill 是 `v0.x`（完善中）—— **可直接改，不必事先确认，改完回报改了哪里**；
若已被用户点头转 `v1.0+`，则任何改动都要先说清"改哪个文件、删什么、加什么"再动手。
本机 skill 规则见 `~/.skills/store/local/local-skills-hub/SKILL.md`。
内容规范：不写日期、不写 changelog、不放会过期的数据（体积/条数这类数字不要写进来）。

**一句话**：机器负责"找出可疑的"，人负责"决定删哪个"。永远不要自动删照片。

照片查重和普通文件查重是两回事：文件查重比 MD5 就够了，而照片的"重复"往往是
**同一张照片的不同版本**（重压缩、编辑过、换个来源存一份），MD5 完全不同。
所以要用感知哈希找相似，再用像素级比对确认。

> 反过来也成立：**平台自己按 md5 去重的相册（如一刻相册），md5 重复率会接近零**，
> 只剩视觉相似这一类 —— 别指望靠 md5 交差。

## 一、核心：感知哈希（dHash）怎么工作

把图片转成 9×8 灰度，逐行比较相邻像素的亮度，每个位置记 1 或 0，得到 **64 位指纹**。
两张图的汉明距离（不同位的数量）越小，视觉上越像。

它抓的是**低频结构**，所以同一张照片即使改名、重压缩、轻微裁剪，距离依然很小。

### ⚠️ 六种失效场景（必须知道，否则会大量误判）

| 失效场景 | 原因 | 兜底判据 |
|---|---|---|
| **滤镜/色调不同** | 灰度化丢掉了颜色信息 | 改用 **RGB 三通道**比对（不要用灰度） |
| **局部差异**（截图状态栏时间、画面里一小块变了） | 缩到 64×64 后差异被平均掉 | 提高到 **128×128**，并加**分块最大差异**（分成 8×8 块，取最差那块） |
| **暗色/纯色图** | 全黑图相邻像素差是随机的，任意两张暗图都"像" | 加**信息量门槛**：灰度标准差 < 8 的不参与匹配 |
| **简单图形**（软件 UI 按钮、皮肤素材） | 结构都极简，彼此都像 | **领域过滤**：排除软件/教程/游戏目录，它们不该是候选 |
| **视频截帧** | 相隔几秒的两帧构图几乎一样 | 用**文件名时间戳**兜底：时间戳不同 = 不同时刻的画面 |
| **连拍 / 同界面截图** | 同一场景连拍，或同一 App 不同时刻的截图 —— 画面极像但内容不同 | **分块最大差异 block_max**（见下）+ **文件名时间戳冲突** |

**单靠哈希距离一定会误判。** 正确组合是：
信息量门槛 + 领域过滤 → dHash 粗筛 → RGB 像素级复核 + 直方图校验 + **block_max** + **时间戳冲突**。

> ⚠️ **直方图相关性对连拍无效，别拿它当连拍判据。**
> 连拍时天空、背景、衣服的颜色全都没变，只有人脸那一小块变了 ——
> 直方图统计的是**全局颜色分布**，这份分布几乎不动，相关性掉不下来。
> 实测连拍组的直方图相关高达 **0.9977 / 0.9991**，比不少真重复还高；
> 同一 App 相隔半个月的两张截图同理（0.9999）。这两类当时都被判成了"确认重复"。

### 判据：分块最大差异 block_max

把归一化后的 **128×128 切成 8×8 块（每块 16px）**，逐块算平均绝对差，**取最差那块**。

- **重压缩副本**：整图均匀地差一点点 → block_max 很小
- **连拍 / 局部改动 / 水印贴纸**：背景全对、只有某一块差很多 → block_max 明显偏大

全图平均差对这两类**可能一样大**（实测：连拍组 rgb 3.87、真重复组 rgb 3.9），
**只有"分块取最大"能把它们分开**。

> ⚠️ **提高比对分辨率解决不了这个问题。** 实测 128 → 256 → 384，
> 两类样本的数值只是**等比放大**，相对间距不变，照样分不开。别把时间花在调分辨率上。

**配套的第二条独立门槛：文件名时间戳冲突。**
用 `((19|20)\d{6})[_-](\d{6})` 从文件名抠拍摄时刻；两边都能抠出且**不相同** → 直接排除。
连拍必然命中（`IMG_..._133141` vs `IMG_..._133142` 差 1 秒）。

> EXIF 里的 `date_time` **不可靠** —— 重新导出会重写它，同一张照片的副本可能带着不同时间。
> 优先用**文件名**里的时间戳；抠不到就退回 block_max 判断，别硬拦。

### 判定阈值：**双档制**，不要只调一个阈值

这类指标的分布是**连续过渡**的，没有一个"天然分界"能一刀切开。
所以正确产出是两档，并且**两档成员互不重叠**：

```
确认重复（可删冗余）：整组两两  rgb128 ≤ 2.5  且  直方图相关 ≥ 0.99
                     且  block_max ≤ 1.5  且  无文件名时间戳冲突
疑似相似（仅供参考，不可用于删）：仅 dHash 接近，或只过了部分门槛
```

- **确认重复** → 默认按建议预选（删多余、留一张）
- **疑似相似** → **默认全部保留**，只供人工看

实现顺序：**先聚"确认档"，再把未进确认档的节点单独聚一次作疑似档** —— 这样两档不会重叠
（否则一个节点会同时出现在两档里，用户看到两张一样的卡片会懵）。

阈值宁可保守 —— 漏判只是少删几张，误判是丢照片。
同一条原则要落到 UI 上：**疑似档不允许出现预选的删除项**。
生成后自检一句"疑似档里 `action=delete` 的组数必须为 0"，几行代码的事，别省。

## 二、流程

### 阶段 1：建指纹库

遍历图片，记录 `路径 / dHash / 原始尺寸 / 文件大小`。

**坑**：如果在 `resize()` **之后**才取 `im.size`，记下来的就是缩放后的尺寸（比如全是 `9x8`）。
这会让所有依赖尺寸的判断（长图折叠、"分辨率更高"的理由）全部失效。
必须在 resize **之前**取原始宽高。

### 阶段 2：粗筛 + 精细比对

1. **粗筛**：dHash 距离 ≤ 阈值（8 左右），取前 25 个候选
2. **精细**：对候选依次算 RGB 128×128 平均差 → 直方图相关性 → **block_max**
3. **时间戳冲突**：两边文件名都能抠出拍摄时刻且**不相同** → 直接否决
4. 全部通过 → "确认重复"；只过一部分 → 留作"疑似"

先用粗筛把 O(n²) 降到可接受规模，再对少量候选做昂贵比对——
几万张图直接两两精细比对是不现实的。

**性能提示**：block_max 是最贵的一步（要遍历 64 个块 × 每块 16×16 像素）。
放在**最后**做，让前面几道便宜的先筛掉大部分候选；给 RGB 归一化结果配一个几百条的小缓存，
能省掉大量重复解码。粗筛本身用 `bin(a ^ b).count("1")` 算汉明距离就够快，
上万张两两比也是几十秒量级。

### 阶段 3：聚类

**不要用单链接聚类**（A≈B、B≈C 就算同一组）。
传递性会把整条链并成一个巨大的组——实测出现过"551 张合成一组"的荒谬结果。

用 **complete-linkage**：要求新成员与组内**所有**成员都相似才加入。

### 阶段 4：生成交互审阅工具

产出单文件 HTML，让用户逐组确认。**这是不可跳过的环节**——
照片是私人资产，机器给的是候选，决定权在人手里。

工具必须具备：

**看**
- 内嵌预览（320px 左右够用），长图/竖图**限高折叠**（否则一张图撑满几屏，翻不动）
- 「查看原图」链接：`<file:///路径>` 直接开全分辨率
- 「打开文件夹」：跳到所在目录，方便在资源管理器里核对

**选**
- 每组一个状态：保留某张 / 全部保留 / 全部删除
- 默认按建议预选好，用户点一下就能改
- 「已看过」标记：点卡片、点原图、切换状态都算看过（**看了但沿用默认也算**）

**判断依据**
- 每张图下方给出**建议 + 简短理由**（绿底=建议保留，红底=可删）
- 理由要分情况，别在两份完全等价时还写"体积最大"：
  - 尺寸和体积都一样 → "内容一致，两份等价，留哪份都行"
  - 尺寸相同体积不同 → "同尺寸下体积最大，画质最完整"
  - 体积相同尺寸不同 → "分辨率更高"

**省事**
- 批量按钮：按类别/判定一键处理（例如"软件资源全部保留并标记看过"）
- 筛选：按类型、判定、是否已看过
- 顶部显示进度（已看 X / 总数），每类标签上也显示

### 阶段 5：导出与执行

- 导出结果必须是**完整主键清单**（本地=绝对路径，云盘=文件 id），不能只给组号
- 用户把清单发回来后，按清单执行（**不要用组号**——算法一迭代组号就变，会删错）
- **导出只能包含"已看过"的组**：用户没看完就导出的话，未复核的组会按默认建议混进待删清单。
  导出前弹一次确认，明确写出"还有 N 组没看过，不会进清单"
- **执行前三重校验**，缺一不可：
  1. 主键在**最新**清单里仍然存在（远端可能已经变了）
  2. 文件名 + 体积与清单一致 —— 防主键串位（id 复用 / 清单过期）
  3. **每组至少保留一个** —— 让"整组消失"在结构上不可能发生
- 走隔离区 + 日志（追加模式），可回滚。
  没有隔离区时（例如云盘直删），把完整清单（含路径 / md5 / 尺寸）**存档一份**留作事后对账

> **云盘场景额外一条：先按扩展名排除视频。**
> 视频缩略图是**首帧**，相隔几秒的两段录像构图几乎一样 —— 必然误判。
> 实测出过 `IMG_1099.MOV(11:10:15)` 与 `IMG_1100.mp4(11:11:10)`、
> `VID_20240727` 与 `VID_20250124`（**相隔半年**）都被判成一对。
> 判类型要看**扩展名**，不要信平台给的分类字段 —— 实测某相册的 `category=3` 里同时混着图片和视频。
>
> **云盘还有一个便利**：多数云相册的详情接口会返回每项的 **md5**。
> 先按 md5 分一遍组（零下载成本），再对剩下的做感知哈希 —— 能省掉一大截计算。
> 但别指望它 —— 平台自己按 md5 去重时，这一层会几乎为空。

## 三、交互工具的实现陷阱

这些是真实踩过的坑，每一个都会让工具看起来"莫名其妙"：

**1. 组 ID 必须稳定**
不要按遍历顺序编号。用 `md5(组内所有路径排序后拼接)[:8]`。
否则每次重新生成，组号都变，用户记的"第 32 组"会指向别的内容。

**2. localStorage 不能用数组索引做键**
存 `{0: true, 1: false}` 这种，数据一变（比如缩略图从 184 张减到 38 张）就全错位，
统计会算出**负数**（`38 - 146 = -108`）。
用**文件名/稳定 ID**做键，并且加**数据指纹**：数据变了就丢弃旧进度。

**改动语义后要顺手升一次 key 版本**（`..._v2_<指纹>`）。
否则上一版留下的脏进度会原样套到新数据上 —— 典型症状是"我明明没看，却显示已看 N 组"。

**3. 卡片整体可点击时，内部按钮必须阻止冒泡**
`<div onclick="选择">` 里嵌 `<a>`/`<button>`，不写 `onclick="event.stopPropagation()"`
就会在点击按钮时误触发卡片的选择。逐个检查所有内层元素。

**4. 生成 PowerShell 脚本时禁用 Python f-string**
f-string 会把 PS 的 `"{0}"` 当成**表达式 `0`** 求值并静默替换成字面量，
结果脚本显示的全是假数字（"待处理: 0 个文件"）。
用普通字符串 + `.replace('__KEY__', val)`。

**5. 点击后只重绘该组，但监听器必须用事件委托**
整页重绘会让滚动位置跳回顶部，用户每点一次都要重新滚回去 —— 所以只局部替换该组的 DOM。
**但这里藏着一个连环坑**：如果给每个组节点**单独** `addEventListener`，用 `replaceWith` 换上的
**新节点是没有监听器的**，用户第二次点击就失效 —— 表现为"选了之后就不能改选、也不能取消"。
正解：**在 `document` 上绑一次事件委托**，靠 `data-*` 属性路由到具体组。

**6. `file://` 链接要保留冒号和斜杠**
`quote(path, safe="/:")`，否则 `G:` 被编码成 `G%3A`，链接打不开。
另外这类链接在 http 环境（预览面板）会被浏览器拦截——**提醒用户双击文件用浏览器打开**。

**7. 预览图内嵌 base64，别指望相对路径**
`<img src="_thumbs/xxx.jpg">` 这种相对路径只在"双击用浏览器打开、且图片就在 HTML 同目录"时才有效；
一旦走 http 预览（IDE 预览面板、localhost）大概率 404，用户看到的是一片空白图片位。
把预览图缩到 260px 左右、JPEG q80 后 **base64 内嵌**，单张约 10 KB，几百张也就几 MB ——
换来的是**无论怎么打开都能看到图**。（「看大图」可以仍旧用相对路径，那是不影响主流程的增强项。）

**8. 批量操作的"占位项"必须有守卫**
批量下拉框的第一项通常是占位文本（`<option value="">批量标记…</option>`）。
处理函数若只写了 `if (v=="dup") …` / `if (v=="sus") …` 而**没先拦空值**，
那么占位项被选中时两个分支都不进，代码径直走到后面那句"标记为已看过"——
**一次 change 事件就把全部组标成已看**，进度显示 100%，而用户明明没看。
守卫一行：`if(!v) return;`，处理完再把 select 重置回占位项。

**9. 改完跑一次自检，别靠手点**
把纯逻辑（分组状态、保留集/删除集、空值守卫）抽出来，用 node 跑几行断言。
最少覆盖这几条：初始默认保留建议那张、能连续改选、撤销后回到建议、空值不标已看、
**疑似档预选删除数 = 0**。比在浏览器里手点快得多，也比"看起来没问题"可靠。
（注意：生成 HTML 时若用 Python 普通字符串拼 JS，JS 里的 `\n` 会被 Python 先转成真换行 ——
要写 `\\n`；Windows 下写文件还要固定 `newline="\n"`，否则 CRLF 会让后续正则校验对不上。）

## 四、缩略图 → 原图匹配

找"这些缩略图对应哪些原图"是同一套技术的另一个用法，但要额外注意：

- 缩略图本身可能是**裁切过的**（16:9），比对时会引入偏差，阈值要放宽
- 匹配结果**必须并排显示**给用户核对（左缩略图、右匹配到的原图），
  只给一个"有原图"标签等于没给——用户无法确认
- 附上**匹配距离**（像素差、dHash、直方图），让用户判断可信度
- 找不到原图的缩略图要**明确标出"原图已丢失"**，它们是唯一副本，默认保留

## 五、脚本

`scripts/photo_dedup.py` —— 阶段 1+2+3 的通用实现：
建指纹库（含正确的原始尺寸）、信息量过滤、领域过滤、
dHash 粗筛 + RGB/直方图/block_max 精细比对 + 文件名时间戳否决、complete-linkage 聚类，
输出 `photo_hash.csv` 与 `dup_groups.csv`（含 `verdict` / `block_max` 列）。用法见脚本头部注释。

判据按「**便宜的先上、贵的放最后**」排列：
汉明距离 → 时间戳冲突 → RGB 平均差 → 直方图 → block_max。

| 参数 | 默认 | 作用 |
|---|---|---|
| `--d-max` | 8 | dHash 粗筛阈值 |
| `--rgb-max` | 2.5 | RGB 128×128 平均差上限 |
| `--hist-min` | 0.99 | 直方图相关下限 |
| `--block-max` | 1.5 | **分块最大差异上限**（挡连拍 / 水印 / 局部改动） |
| `--no-ts-guard` | 关 | 关掉文件名时间戳冲突否决（默认开启） |
| `--min-std` | 8 | 信息量门槛 |
| `--mode cross` | `all` | 只查跨根目录的重复（如「本地 vs 云盘导出目录」） |

**动这两条门槛时必须做对照测试**，做法是拿**同一份内容**复制成「时间戳相同」和「时间戳不同」
两份，再配一对连拍：
- 默认参数跑 → 时间戳不同的那份和连拍对都应该被挡住，只剩正品那一组
- 放开门槛（`--block-max 100 --no-ts-guard`）→ 它们应该立刻漏进来

只看"总组数没变"说明不了任何问题 —— 别的门槛会替你挡掉，看起来"没问题"。
要能指出**是这条门槛在挡**，才算验证过。

**云盘场景**：输入不是本地目录，得先用平台接口拉清单 + 缩略图。
注意缩略图直链通常带 `expires`（常见 2 小时），**抓完清单要尽快下载**；
隔夜再下会成片 403 —— 重跑一次清单刷新即可（下载器按文件存在与否跳过已缓存的）。
