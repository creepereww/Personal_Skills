# 手机导出媒体库：时间恢复与归档

**改我时要守什么**：本 skill 是 `v0.x`（完善中）—— **可直接改，不必事先确认，改完回报改了哪里**；
若已被用户点头转 `v1.0+`，则任何改动都要先说清「改哪个文件、删什么、加什么」再动手。
本机 skill 规则见 `~/.skills/store/local/local-skills-hub/SKILL.md`。
内容规范：不写日期、不写 changelog、不放会过期的数据（体积/条数/版本号这类数字不要写进来）。
本 skill 只写**方法**，具体盘符、目录、批次数字一律放项目自己的工作文档。

**一句话**：先把「时间」修对，再谈归档和去重；任何删除都要能回滚。

## 边界：什么时候用哪个 skill

| 场景 | 用谁 |
|---|---|
| 手机分批导出、时间戳被改写、按年月归档、ZIP 相册包 | **本 skill** |
| 同一张照片的重压缩/连拍/相似图、要人工逐组勾 | `local-photo-dedup-review` |
| 全盘通用文件整理、目录级映射、跨盘归类 | `local-file-dedup-organize` |

## 一、六条铁律

**1. 头尾指纹不能作为删文件的依据。**
「大小 + 头尾若干 KB 的 SHA-256」看着省事，但中间不同的文件照样被判成重复 —— 抽查过一批候选，
真一致的只有九成，剩下全是误判。只用于**预筛候选**，判定必须回到**全量 MD5 / SHA-256 双向比对**。

**2. 删除前逐对全量复核，删除走回收站。**
清单生成后另写一支核验脚本，对每条待删项与保留项重算哈希，两个方向都一致才进删除队列。
用系统回收站 API，不用 `rm` / `del /F`。删完回读计数，0 成功 / N 失败要当成失败而不是「已完成」。

**3. 每次动作都留可回退台账。**
原路径 → 新路径、原时间 → 新时间、日期来源、批次来源，逐条写 CSV（UTF-8-BOM，Excel 直接开）。
台账是追加的，多次执行不能覆盖历史。用户问「之前删的有没有误删」时，靠它复核而不是靠记忆。

**4. 预演先行，且预演范围必须与正式执行同构。**
脚本默认 dry-run，`--apply` 才落地。递归收集来源时**必须排除已归档的年份目录和重复区**，
否则已归档文件会被当成新文件，预演数虚高一大截。
分批导出时来源要**递归扫相册子目录**（相册/相机/视频编辑/微信等），只扫根目录散落文件会整批漏掉。

**5. ZIP 解压后逐条校验全通过，才允许删 ZIP。**
条目数、每条大小、CRC32（必要时再加 MD5）全部对上，才把压缩包移进回收站。
一条不过就保留整包，不要「大部分对上了就删」。

**6. 大改先说明，小改直接做。**
删章节、重写、拆分结构、改挂载范围要先说清「改哪个文件、删什么、加什么」等确认；
错别字、补一行、修失效路径可直接做。用户提出方向 ≠ 批准方案。

## 二、日期：这是整套流程的核心

### 优先级（从高到低，写进代码就照这个顺序）

```
1. EXIF DateTimeOriginal (0x8769 子 IFD 里的 36867)   可信
2. 文件名里的时间戳                                    可信
3. EXIF DateTimeDigitized (36868)                      可信
4. 所在文件夹名里的年月                                中等
5. mtime                                               低可信，标注
6. EXIF DateTime (306)                                 最低，标注
```

- `mtime` **不能当兜底**：导出、复制、解压都会重写它，实测与文件名日期同日的比例只有一半左右。
  先建一个 `BAD_MTIME` 集合（导出当天、批量处理当天），命中就整体跳过 mtime。
- TIFF **306 是 `DateTime`（图像被写入/后处理的时间），不是 `Software`(305)，更不是拍摄时间**。
  常被导出和修图软件重写，与拍摄日差异很大，只能垫底且必须在台账标注「低可信」。
- 台账一定要有 `日期来源` 列。用户后续想重算、想剔除低可信项，全靠这一列。
- 定时失败的文件单独进 `00_无法定时/`，**不要硬塞一个猜测日期**。

### 三个提取器的实现要点

**EXIF**：标签在子 IFD `0x8769` 下，36867 = `DateTimeOriginal`、36868 = `DateTimeDigitized`；
顶层 306 = `DateTime`、305 = `Software`。用标准库解析 TIFF 头即可，不必依赖第三方图像处理库。
值形如 `YYYY:MM:DD HH:MM:SS`，注意冒号不是短横线。

**MP4 / MOV**：`moov/mvhd` 里的创建时间是 1904 纪元秒数，按本地时区换算。
**`moov` 可能在文件尾部**，只读头部几十 KB 会大量漏读。可靠做法：
先头 64 KB + 尾几 MB 扫 `mvhd`；再不行按**顶层原子遍历**定位 `moov`（读 size/type 逐个跳）。
不要因为「读了头没有」就判为无时间。

**文件名**：覆盖 `YYYYMMDD_HHMMSS`、`YYYY-MM-DD_HH-MM-SS`、内嵌 13 位毫秒 epoch。
13 位数字必须要求两侧是非数字（否则会从长串 ID 里抠出假年份）；**纯数字文件名直接放弃猜测**，
交给 mvhd，避免把订单号/ID 当成日期。

**改创建时间**：Python 的 `os.utime` 只能改 atime/mtime；
Windows 的 CreationTime 要用 PowerShell `(Get-Item ...).CreationTime = ...`。

## 三、流程

| 阶段 | 做什么 | 产出 |
|---|---|---|
| 0 | 对齐范围：只整理哪一类？原件保留还是移动？备份要不要（用户常明确说不要） | 一句话确认 |
| 1 | **只读盘点**：递归列全库，含 ZIP 内的条目清单 | 全量清单 CSV |
| 2 | **时间恢复**：按优先级定时，写来源；旧库时间校正写可回退台账 | 时间台账 + 无法定时清单 |
| 3 | **全量去重**：大小预筛 → 全量 MD5，显式设计「保留方」优先级 | 重复清单（保留/待删标注） |
| 4 | **按年月归档**：预演 → 用户确认 → `--apply` | 归档台账 |
| 5 | **增量批次**：新批次与库比对，只合入新增，空来源目录清理 | 批次记录 |
| 6 | **ZIP 处理**：解压 → 逐条 CRC/大小/MD5 校验 → 全通过才移回收站 | 校验报告 |
| 7 | **完整性审计**：索引悬空、历史删除复核、回读计数 | 审计结论 |
| 8 | **交付**：全量台账、重复清单、可回退映射、Markdown 报告 | 一叠 CSV + 报告 |

「保留方」优先级要**显式写死**而非随机：可信来源 > 层级浅 > 有 EXIF > 时间校正过。
跨盘合并时先全库复制建统一库，再清理旧重复；C 盘原件是否保留由用户定，别自作主张删。

## 四、踩过的坑（每一条都造成过真实返工）

| 坑 | 后果 | 对策 |
|---|---|---|
| 大小 + 头尾指纹判重复 | 一批误判，差点删掉不同内容的文件 | 只作候选；判定用全量哈希双向复核 |
| 递归收集把年份目录也扫进去 | 预演虚报几百个「新文件」 | 来源 = 根下直接文件 + 非年份/非重复区的相册子目录 |
| 只扫根目录散落文件 | 助手按相册建子目录时，**整批漏检** | 来源递归，归档后清掉空相册目录 |
| `mvhd` 只读头部 | 视频大量读不到拍摄时间 | 头 + 尾扫，再顶层原子遍历找 `moov` |
| 拿 mtime 兜底 | 归档年份大批错 | 撤掉；建 `BAD_MTIME` 跳过导出日 |
| 绝对路径又 `Join-Path` 一次 | 拼成 `G:\G:\...`，**0 成功 / 全失败** | 删前打印 3 条完整路径核对；删除后看成功/失败计数 |
| 回收站计数用错转义（`'\$R'`） | 明明删了却报 0 | 用 `-like '$R*'` 这类通配，别手写转义 |
| 重复项删除后索引没更新 | 上千条悬空记录 | 索引加「状态」列，保留/已删除 |
| 台账状态列混入扩展名 | 分类统计错乱 | 由扩展名统一重新归类，别手写 |
| 跨盘全量 MD5 前台跑 | 超时被 SIGTERM，白跑 | 长任务后台跑，进度写日志 |
| Python f-string 生成 PowerShell | PS 的 `"{0}"` 被求值成 `0`，数字全是假的 | 普通字符串 + `.replace('__KEY__', val)` |
| 只信脚本自己打印的「成功」 | 实际一个文件没动 | 改完回读验证：计数、路径、哈希 |
| 生成 HTML/报告时用 Edit 匹配换行 | 换行符不一致导致匹配失败 | 用脚本读写整文件 |
