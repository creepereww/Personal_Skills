# 文档规范基线（非代码项目版）

> 本文件由 `SKILL.md` 按需引用，**不进 Agent 上下文**——只在需要建文档或审查文档质量时才读。
> 原版基线面向软件项目（11 板块里有 4 块是代码专属）。本版保留通用部分，标注了每块对非代码项目的适用性。

## 一、规则文档（CLAUDE.md / AGENTS.md / 你的 `整理规则.md`）

**它是什么**：给一位聪明但不了解背景的 AI 新同事写的"入职手册 + 行为准则"——用具体、可执行的语言，把"这个项目是什么、怎么做事、绝对不能做什么"一次性说清楚。

**原版 11 个板块，逐块标注**：

| # | 板块 | 内容要求 | 非代码项目 |
|---|------|----------|-----------|
| 1 | 项目简介与核心目标 | 1-3 行说清是什么、解决什么问题 | ✅ 直接可用 |
| 2 | 技术栈与关键依赖 | 语言、框架、版本 | ❌ 无代码 |
| 3 | 项目结构与架构说明 | 顶层目录职责、模块划分 | ✅ 改为「目录结构与职责」 |
| 4 | 开发环境 & 常用命令 | install/dev/test/build 速查 | ⚠️ 改为「操作速查」 |
| 5 | 代码风格与规范 | 命名、文件组织、lint | ✅ 改为「命名 / 分类 / 编号规则」 |
| 6 | 测试要求 | 框架、覆盖率、运行方式 | ❌ |
| 7 | Git 工作流与提交规范 | 分支、commit、PR | ⚠️ 有 git 才算 |
| 8 | 关键设计原则与约束 | 硬边界、禁止事项 | ✅ 放红线，最核心 |
| 9 | AI 代理行为守则 | AI 必须遵守的规则、禁止操作 | ✅ 放只读扫描 / 确认 / 回收站 / 备份 |
| 10 | 常见陷阱 & 已知问题 | 踩坑警示、已知 bug | ✅ 只留"下次会踩"的坑 |
| 11 | 其他 | 项目特有的必要信息 | ✅ 先问"是不是真必要" |

**非代码项目的推荐 6 块**（把 3、4、5 改造后的版本）：

1. 这份规则管什么（1-3 行）
2. 目录结构 —— 每个目录放什么、不放什么
3. 硬边界与红线 —— 什么绝对不能做
4. AI 行为守则 —— 操作前必须做什么
5. 命名 / 分类 / 编号规则
6. 常见陷阱 & 已知问题

**质量红线**（比板块清单更重要）：

- **简练不重复** —— AI 靠这个文件指导行为，冗余 = 遵守率下降
- **具体可执行** —— "Desktop 根目录不许新建文件夹" ✅ / "注意文件整洁" ❌
- **不是变更日志** —— 不含"X 日起改成 Y 规则"这类历史叙事，那是 git log 和 CHANGELOG 的活
- **尺寸 ≤300 行 / ≤15KB**，单次同步净涨幅 ≤30 行

## 二、说明文档（README.md / docs/）

**它是什么**：告诉人类和其他 Agent"这东西能做什么、怎么用"。站在第一次接触项目的人的视角写。

| # | 板块 | 内容要求 | 非代码项目 |
|---|------|----------|-----------|
| 1 | 项目名称与徽章 | 名称 + badge | ⚠️ 徽章是开源项目才需要 |
| 2 | 简介 / 概述 | 一句话说清是什么 | ✅ |
| 3 | 功能特性 | 核心功能 3-8 条 | ✅ |
| 4 | 演示 | 截图 / GIF / demo 链接 | ⚠️ 看情况 |
| 5 | 快速开始 | 命令可直接复制运行 | ⚠️ 改为「怎么用」 |
| 6 | 使用文档 / API 参考 | 用法示例 + 指向 docs/ 的链接 | ⚠️ 改为「操作手册」 |
| 7 | 配置 | 关键配置项 | ⚠️ |
| 8 | 开发 / 贡献指南 | 面向人类贡献者 | ❌ |
| 9 | 许可证 | 开源协议 | ❌ |
| 10 | 致谢 / 相关项目 | 链接 | ❌ |
| 11 | 其他 | 项目特有信息 | ✅ |

**质量红线**：

- 命令可复制运行，每条都要指定运行目录
- **不与规则文档重复** —— 说明文档说"能做什么"，规则文档说"怎么做事"
- 细节链接到 docs/，说明文档只放最核心的部分
- 面向新手 —— 站在第一次接触的人的视角

## 三、docs/ 目录与命名规范

**两种组织方式**，按实际情况选：

```
方式一：按用途分（大多数项目）
docs/
├── index.md               # 索引入口
├── structure.md           # 结构说明
├── getting-started.md     # 怎么用
├── CHANGELOG.md           # 变更日志
└── faq-troubleshooting.md # 常见问题与排错

方式二：按模块分（多模块项目）
docs/
├── index.md
├── modules/<模块名>/...
└── shared/...
```

**命名规范**：

| 规则 | 说明 |
|---|---|
| 小写 + 连字符 | `getting-started.md`，不用 `GettingStarted.md` |
| 统一 `.md` | 易渲染、易对比 |
| 数字前缀排序 | `01-intro.md`、`02-setup.md` |
| 一个文件一个主题 | 别让一个文件既讲安装又讲 API |
| 索引用 `index.md` | **不要用 README.md**，会跟项目根 README 混淆 |

## 四、从零建立时的建文件顺序

按优先级，**先修不一致、再新建**（错误信息比缺失信息危害大）。新建时按受众从外到内：

| 顺序 | 动作 | 理由 |
|---|---|---|
| 0 | 修不一致（🔴） | 错误信息比缺失信息危害更大 |
| 1 | 建 `docs/` | 外部受众，改错影响最大 |
| 2 | 补规则文档 | AI 受众，决定后续所有行为 |
| 3 | 写 / 改说明文档 | 全人类受众 |
| 4 | 迁移散落文件、清理废弃 | 收尾 |

这个顺序的用意：**先动外部优先级最高的**——中途被打断时，读者看到的也是已对齐的最新状态。

每建完一个文件立即做一致性校验：文档里写的每条事实，都能在交付物里找到对应。
