## 补记 helper-selector 凭证弹框坑（→ 写进 skill）

**起因**：昨日 push 三次卡住被 SIGTERM，真因查明 —— WorkBuddy 内置 PortableGit 的
**system 级 gitconfig 写死 `credential.helper=helper-selector`**，需要凭证时弹出 GUI 选择框；
非交互模式（`GIT_TERMINAL_PROMPT=0`）只挡命令行提示、**挡不住 GUI** → 卡到超时被杀。
关键机制：`credential.helper` 在 git 里是**累加**的，system 那条排在 local 之前先被调用。

**根治**（仓库 local config，不动 system 级）：先清空、再只留 GCM：

```bash
git config --local --replace-all credential.helper ""
git config --local --add credential.helper "<GCM 路径>"
```

验证：`printf "protocol=https\nhost=github.com\n\n" | GIT_TRACE=1 git credential fill`，
只出现 `git-credential-manager` 即干净。已对本仓库设好。

**落点**：

  新增一节「git 凭证：会弹 GUI 框卡住 push」（症状 / 根因 / 修法 / 验证 + "push 卡住不一定是
  网络"的判据）；description 同步补一条。放这里是因为根因是 **WorkBuddy 客户端特有**
  （system gitconfig 来自它的 PortableGit），不属于跨机器通用范畴。

## 新增 scripts/push.ps1（推送前自动同步）

**动机**：用户问「每次 push 时有没有做 pull 检测」—— 查明**没有**：这几轮都是 commit → 直接 push。
git 会挡非快进推送（不会静默冲突/丢数据），但 push 被拒后仍要手工 fetch + merge，**那时才可能冲突**。

**做法**（用户选方案 3：固化成脚本）：`scripts/push.ps1`，顺序 **fetch → 落后则 rebase → push**，
把之前散落的推送坑一次封装：

1. 自动绕开指向 `127.0.0.1` 的沙箱代理（真代理不动）
2. TLS 后端在 `openssl` / `schannel` 之间**交替重试**
3. github.com:443 时通时断 → 最多 6 次重试
4. 推前 fetch 检测，落后就 rebase（工作区脏则中止；冲突不自动 abort，停在现场）

开关：`-DryRun` / `-NoRebase` / `-KeepProxy` / `-Branch` / `-Remote` / `-Log`。
⚠️ 与已有的 `pull.ps1` **无关**（那个是"拉上游 skill 到 store/cache"）。

**实测**：语法 OK；dry-run 跑通 —— 第 1 次 openssl 失败、第 2 次自动换 schannel 成功；
`push --dry-run` 确认凭证链能认证（GCM 取到凭证，不弹框）。

## 重大发现：本机有两个 git，system 配置不同

- **bash** `which git` → PortableGit 的 `/mingw64/bin/git`（2.55），system config = **`helper-selector`**
- **PowerShell** `Get-GitExe` → `D:\Git\cmd\git.exe`，system config = **`manager`**

这解释了之前所有现象：**「弹凭证框卡住 push」只在 bash 下踩得到**（我手动 push 都在 bash），
PowerShell 脚本走 D:\Git 的 git 就不会弹。两边读的**仓库级 `.git/config` 是同一份**（空值重置 + GCM），
所以实际生效的凭证链都干净。

→ 已补进 `store/machine/wgc-work1-px`（v0.5 → v0.6），并把 `scripts/push.ps1` 的用法写进那节。

**体检判据的坑**：`git config --get-all credential.helper` 会把「已被 local 空值清掉」的 system 值
也列出来 → 直接匹配 helper-selector 会**误报**。正确判据 = system 含 helper-selector **且**
local 里没有 `credential.helper=`（空值行）。脚本已按此实现（用 `--list` 查空值行）——
实测「已固化 → 不报警、未固化 → 报警」。

## ★ 推送失败的真正拦路虎：github.com 被 Watt Toolkit 劫持到 127.0.0.1

**背景**：用户说「已经都推送了」，实测**并没有** —— 远端 `master` 仍是 `26b8f6d`，
本地 `8d8e1b3`（那条"批量：SkillHub 接入 / routing 分组 / push 脚本固化 / jlceda 迁到 connector"）
**领先 1 个提交没上去**。（本轮已补推成功：`26b8f6d..8d8e1b3`，API 复核远端 = `8d8e1b3`。）

**根因链（curl verbose 抓到的硬证据）**：

```
Host github.com:443 was resolved.
IPv4: 127.0.0.1                      ← github.com 被劫持到本机
Connected to github.com (127.0.0.1) port 443
issuer: CN=SteamTools Certificate; O=BeyondDimension; C=CN
server: WattToolkit                  ← Watt Toolkit（Steam++／瓦特工具箱）本地反代
```

- 劫持走的是 **Watt Toolkit 的 DNS/加速**（`hosts` 文件里**没有** github 条目，别去改 hosts 找）。
- `api.github.com` **未被劫持** → 所以 curl 打 API 一直正常，只有 git 的 `github.com` 中招。
- 由此派生两个"假象"：**openssl** 后端报 `unable to get local issuer certificate (20)`
  （被自签 SteamTools 证书骗到）、**schannel** 报吊销检查失败
  （`CRYPT_E_NO_REVOCATION_CHECK`，curl 侧同样复现 → 要 `--ssl-no-revoke`）。

**真正让 push 死掉的一步**：git 先 GET `info/refs?service=git-receive-pack` 拿到 **401**（正常，
GitHub 未认证探测就这样）→ git 调凭证助手 GCM 取凭证 → **然后进程静默 exit 128（stdout/stderr 全空）**。
反代本身是好的：用 **`Basic`** 认证 curl 同一个 URL → **200**，并正确返回 `refs/heads/master`。
（我一开始用 `Bearer` 测，白测了 —— git 协议走 Basic。）

**判定**：不是网络不通、不是 token 失效（token 有效：`creepereww`，scopes `gist, repo, workflow`，
打 `api.github.com/user` 得 200）、不是凭证助手没存（`git credential fill` 能取到）——
是**「401 → 调助手 → 重试」这条路径本机走不通**。

**✅ 可用推法（唯一验证成功的）**：清空凭证助手 + 用 GCM 取到的 token 直接注入 Basic 认证头，
让**第一次请求就带认证**（绕开 401 重试）：

```powershell
$g="D:\Git\cmd\git.exe"; $repo="C:\Users\cgw06\.skills"
$r = ("protocol=https`nhost=github.com`n`n" | & $g -C $repo credential fill 2>&1 | Out-String)
$tok = (($r -split "`n") | Where-Object {$_ -like "password=*"}) -replace "^password=",""
$b64 = [Convert]::ToBase64String([Text.Encoding]::ASCII.GetBytes("creepereww:$($tok.Trim())"))
& $g -C $repo -c "credential.helper=" -c "http.extraHeader=Authorization: Basic $b64" `
   -c http.sslBackend=openssl -c http.sslVerify=false push origin master
```

实测：`26b8f6d..8d8e1b3  master -> master` ✓（`sslBackend=openssl` + `sslVerify=false` 可过反代自签证书）。

**未解/待办**：
- 为什么带凭证助手的路径会**静默 128**，还没定论（试了 helper 带/不带 `.exe`、只留 system `manager`、
  显式 GCM 覆盖 —— **全部 128**，只有 extraHeader 预认证能过）。
- **`scripts/push.ps1` 目前走的是凭证助手路径 → 在这台机上会失败**，需要打补丁
  （预认证头 + `schannelCheckRevoke=false` 之类）才行。
- 临时办法：**关掉 Watt Toolkit 的 GitHub 加速**（或退出 Watt Toolkit）再 push，可能就恢复正常路径。
- `store/machine/wgc-work1-px/SKILL.md` 该补这条劫持事实（本轮尚未补，等用户点头）。

**另一个环境坑**：Bash 侧 git 的所有**联网**操作被静默吞掉（`ls-remote`/`fetch`/`push` 一律 exit 0 + 零输出），
但 **PowerShell 侧同一 git 正常**。→ 本机做网络类 git 操作**走 PowerShell 工具**，别在 Bash 里判断成败
（Bash 里报"成功"是假象）。
