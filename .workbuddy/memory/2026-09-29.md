## ★ 纠正上一条里的错误认识：skill 加载源不是 cache/

用户追问「cache 里的名字叫 skill-expert-manager，会被加载吧？marketplaces 里叫 expert-manager 的会加载吗？」
查出来的结论**推翻了我上一条的隐含写法**：

**权威判据 = `~/.workbuddy/.skill-list-cache.json`**：
- `results[]`（45 条）= 真正生效的技能，每条有 `filePath`（加载源）+ `source`
- `watch.dirs` = 被监视目录列表
- `source` 取值：`userSettings`（用户目录）/ `plugin`（插件）/ `connector`（连接器）

**核心事实**：
1. **插件技能的加载源是 `plugins/marketplaces/<市场>/plugins/...`，不是 `plugins/cache/`。**
   实证：`agent-browser` 的 `filePath` = `marketplaces/codebuddy-plugins-official/plugins/agent-browser/SKILL.md`。
2. **`cache/` = 已安装副本 + 会话引用计数，不是运行目录**：
   - `.in_use/<pid>`（内容 `{"pid":...,"procStart":...}`）→ 该版本正被引用
   - `.orphaned_at` → 已被新版取代待清理（`skill-expert-manager/0.1.0/` 就带这个）
3. **那么 `marketplaces/workbuddy-builtin/skills/expert-manager` 会被加载吗？**
   仅当它在 `skill-list-cache` 里出现才加载；`skill-expert-manager` 当前**不在** 45 条清单里
   （即未被加载 —— 它是我按需调用的内置技能，走的是另一套 builtin 注入机制）。
4. **两个名字对不上是正常的**：`marketplace.json` 的 `name` = `skill-expert-manager`（市场名，带前缀），
   源目录 = `expert-manager`（无前缀），靠 `source: "./skills/expert-manager"` 关联。

**另外纠正一处**：`cache/` 与 `marketplaces/` 里的同名插件是**两份独立文件**（大小/时间均不同），
不是 junction/symlink（实测 `st_file_attributes=0x10` 无 `0x400` reparse 标志）。

以上均已写入 `local-windows-shell-conventions` **v0.3**（重写了那两节，纠正 v0.2 的隐含错误）。

## ★ 推送 GitHub 踩坑与解法（本机，重要）

用户要求「整理 + push，要回家那台同步」。commit 秒成，**push 卡了很久**，四个坑叠加：

1. **WorkBuddy 沙箱注入代理** `http_proxy=http://127.0.0.1:58185` —— 该代理对 **`github.com` 返回 502**

2. **`http.sslBackend=schannel`（Git for Windows 默认）报** `schannel: server closed abruptly (missing close_notify)`。
   → 改 **openssl** 后端就通。
3. **`credential.helper=helper-selector`**（来自 WorkBuddy PortableGit 的 system gitconfig）
   在非交互环境**卡住等 GUI 选凭证**（push 挂起直到 120s 被 SIGTERM）。

   `could not read Username for 'https://github.com': terminal prompts disabled`。
   **必须显式指定 GCM 当凭证助手**（里面已存 `creepereww` 的 token，可用
   `echo -e "protocol=https\nhost=github.com\n" | /mingw64/bin/git-credential-manager get` 验证）。
4. `github.com:443` 本身**时通时断** —— 一次不行就重试（实测常在第 2~4 次成功）。

